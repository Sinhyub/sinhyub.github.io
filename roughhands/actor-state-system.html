[기술개발] 엑터상태시스템

2016-04-14 · RoughHands 게임 제작기

본 포스트에서는 게임에 등장하는 엑터의 상태를 관리하기 위해 시도했던 방법과 그 최종 결과를 공유하려고 합니다.

엑터상태시스템의 목적

저희 프로젝트에서는 게임 내에서 움직이며 상호작용하는 캐릭터들을 엑터(Actor)라고 불렀는데, 이 엑터들의 상태(공격 중, 이동 중, 대기 상태, 방어 중, …)를 관리하는 시스템이 필요했습니다.

이 시스템의 목적은 엑터가 어떤 행동을 수행하도록 요청받았을 때:

  1. 그 행동이 엑터의 현재 상태에서 가능한 일인지 불가능한 일인지 판단하는 것
  2. 가능하여 행동이 수행된 경우, 수행된 행동에 맞는 상태로 엑터의 상태를 변경하고 관련 작업을 수행하는 것

예를 들자면, 엑터는 대기 중이거나 이동 중일 때는 스킬을 시전하는 것이 가능하고 공격 중이거나 공격당하는 중일 때는 스킬을 시전하는 것이 불가능합니다.

엑터상태시스템 설계 (1차)

최초 설계시에는 행동의 가능/불가능을 판단하기 위해 다음 방법을 사용했습니다:

  1. 엑터상태시스템 내부에 현재 상태(A)를 기록
  2. 입력값으로 요청한 행동이 수행되었을 때의 결과 상태(B)를 입력
  3. 정해진 규칙을 확인하여 현재 상태(A)에서 다음 상태로 올 수 있는 상태 중 결과 상태(B)가 포함되어 있는지 확인
  4. 가능/불가능 여부를 리턴

그런데 해당 설계에는 다음과 같은 문제가 있었습니다:

1. 규칙이 언제나 원하는 결과를 주지는 않는다

상태 A에서 상태 B로의 변경이 언제는 가능하고 언제는 불가능하여 판단이 명확하지 않은 경우가 많았습니다. 예: 엑터가 Dead 상태가 된 경우 다른 어떤 상태로도 변경이 불가능하다는 규칙이 있었지만, 한 라운드가 끝나고 다음 라운드가 시작될 때는 죽은 엑터를 부활시키기 위해 엑터의 상태를 Idle로 변경해야 합니다.

2. 시스템을 전적으로 신뢰하지 못하게 됨

엑터상태시스템이 반환하는 결과를 그대로 믿지 못하게 되고, 개발자가 시스템 외부에서 직접 조건을 체크하고 처리해야 했습니다. 개발자의 실수 확률 증가 및 기획 변경 시 수정해야 하는 코드 양이 증가했습니다.

3. 엑터의 상태 변경에 관련된 코드가 시스템 외부에 존재

규칙에 위배되는 동작을 수행하기 위하여 상태 변경 코드가 시스템 외부에도 존재하게 되어, 기존 코드 내용 파악이 어려워지고 코드 수정 및 새로운 기능 추가가 복잡해졌습니다.

결론: 언제 어디서 문제가 터질지 몰라서 코드의 신뢰도가 낮았습니다.

엑터상태시스템 설계 (2차)

문제들이 누적되고 코드의 신뢰도가 낮아져 엑터상태시스템을 재구성하기로 결정했습니다.

기존 시스템의 문제는 정의한 규칙이 제대로 된 답을 주지 못하는 것에서 비롯되었다고 판단하고 "트리거"라는 새로운 개념을 도입했습니다.

트리거란 일종의 발생 이벤트를 의미하며, 사용자의 스킬 시전 요청, 사용자의 이동 요청, 다른 캐릭터에게 피격당함 등이 있습니다.

기존 규칙인 "상태 A에 대해 가능한 다음 상태 B를 결정"을 대신하여 "상태 A에 대해 트리거 T가 발생하였을 때의 다음 상태를 결정"이라는 새로운 규칙을 도입했습니다.

예시: 기존 규칙에 의하면 상태 Dead에서 상태 Idle로의 변경(부활)은 항상 불가능하지만, 새로운 규칙의 경우 상태 Dead에서 트리거 NewRound는 다음 상태로 Idle을 리턴하여 캐릭터를 부활시킬 수 있습니다.

새로운 규칙에 맞는 시스템의 동작:

  1. 어떤 행동을 요청할 때 그에 맞는 트리거 T를 엑터상태시스템에 입력
  2. 엑터상태시스템은 현재 상태 A와 입력된 트리거 T를 규칙에서 확인하여 다음 상태를 리턴
  3. 다음 상태에 따라 요청된 행동을 수행하거나 수행할 수 없는 행동임을 알림
  4. 요청된 행동이 수행 가능한 경우 다음 상태로 엑터의 상태를 변경

개선 효과

  1. 규칙에 위배되는 동작을 수행할 필요가 없어짐 — 언제나 원하는 결과를 얻을 수 있는 규칙 생성, 예외 발생 없음
  2. 엑터상태시스템을 전적으로 신뢰 가능 — 시스템 외부에서의 추가 확인 및 처리 불필요
  3. 상태 변경에 관한 모든 내용이 하나의 표로 정리됨 — 규칙이 간단해지고 예외사항 없음, 표 하나로 모든 상태 변경 내용을 한눈에 파악 가능
  4. 코드 수정 없이 표 조작만으로 수정 가능 — 새로운 기획 추가 또는 기존 내용 수정 시 표만 수정하면 됨

교훈

  1. 규칙은 언제나 명확해야 한다
  2. 시스템은 신뢰할 수 있을 때만 의미가 있다
